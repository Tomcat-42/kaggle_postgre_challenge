\begin{abstract}
We optimize the \texttt{jsonb} expansion pipeline of a Python/PostgreSQL application that transforms semi-structured records into normalized relational tables over SSH.
Through profiling-driven query redesign, transaction chunking, and server tuning, we reduce the measured expansion time from 166\,s to 33\,s ($5.0\times$) at $10^6$ source rows, with the speedup increasing at larger scales.
Peak RAM remains at 256\,MB and temporary storage scales linearly with the source table.
The chunked transaction model enables checkpoint-and-resume for failure recovery.
All integrity guarantees are preserved.
\end{abstract}

\begin{IEEEkeywords}
semi-structured data, ETL optimization, PostgreSQL, JSONB, bulk loading, transaction chunking, failure recovery.
\end{IEEEkeywords}

\section{Introduction}
\label{sec:intro}

Many applications that use PostgreSQL store incoming data as \texttt{jsonb} records, taking advantage of the type's flexibility to ingest heterogeneous sources without requiring a fixed schema upfront~\cite{postgresql17, petersen2011json}.
Before this data can participate in queries that rely on joins, constraints, or efficient indexing, it must be \emph{expanded} into a set of normalized relational tables.
This extract-transform-load (ETL) pattern is well studied in general~\cite{vassiliadis2009etl}, but the specific case of expanding large volumes of \texttt{jsonb} rows into multiple interdependent tables, over a remote connection, raises performance and reliability concerns that grow with dataset size.

\emph{PostgreSQL Data Manager} is a Python desktop application designed for this workflow.
It administers PostgreSQL databases on a remote Linux server, communicating exclusively through SSH: the client constructs SQL batches locally, pipes them to \texttt{psql} on the server, and parses the returned output (Fig.~\ref{fig:architecture}).
This remote execution model reflects a deployment requirement where direct access to the database host is not available, and must be preserved in any optimized implementation~\cite{grimm2026}.
The application's \emph{Expand} operation reads a source table of \texttt{jsonb} records, applies a sequence of SQL recipes that populate multiple destination tables, and commits the results in a single atomic transaction.
Because later recipes may join against tables populated by earlier ones, the destinations form a dependency chain: all must succeed together or none at all.

In the benchmark dataset used in this work, each source row carries a \texttt{jsonb} object with 64 keys encoding a mix of identifiers, timestamps, categorical labels, and numeric measurements.
The expansion distributes this payload across six destination tables: two small dimension tables are populated first with distinct reference values, followed by a central fact table that joins against them, and finally three child tables that reference the fact table through foreign keys.
One of the child tables unpivots up to 14 positional entries per source row, so the total number of inserted rows can exceed the source count by an order of magnitude.
A deterministic generator with a fixed seed produces identical records for any requested size, enabling reproducible benchmarks from $10^5$ to $3 \times 10^8$ rows.

Several factors make this expansion non-trivial to optimize.
The entire operation runs as a single SQL batch piped through SSH, so the client has limited ability to interleave work or react to intermediate results.
Each recipe must parse \texttt{jsonb} fields, cast and validate them, and perform joins against tables populated by earlier recipes within the same transaction.
At the scale of hundreds of millions of rows, the working set can exceed available memory, and write-ahead log (WAL) pressure from a single large transaction becomes significant.
Meanwhile, the system must maintain source validation, version registration, and referential integrity across all destinations, so optimizations cannot simply bypass these guarantees.

The baseline implementation is functionally correct but does not scale well, and it offers no recovery mechanism for interrupted operations.
If a network failure or timeout occurs during a long-running expansion, all progress is lost and the database may be left with partial results.
This combination of performance and reliability limitations motivates the present work.

This paper makes three contributions.
First, we profile the baseline pipeline to identify where processing time is spent, using the application's built-in instrumentation and PostgreSQL-side timing.
Second, we apply targeted optimizations to reduce the measured expansion time on datasets ranging from $10^5$ to $3 \times 10^8$ source rows.
Third, we introduce a checkpoint-and-resume mechanism inspired by write-ahead recovery~\cite{mohan1992aries}, allowing interrupted expansions to continue from the last committed batch rather than restarting from scratch.
All optimizations preserve the system's existing guarantees: source and destination validation, version registration, and referential integrity.

Section~\ref{sec:architecture} describes the baseline pipeline in detail.
Section~\ref{sec:methodology} presents profiling results and optimizations.
Section~\ref{sec:conclusion} concludes.

\section{Architecture and Background}
\label{sec:architecture}

This section describes the baseline expansion pipeline, the data model it operates on, and the integrity guarantees that any optimized implementation must preserve.

\subsection{Expansion Pipeline}
\label{sec:pipeline}

The expansion proceeds in four stages, orchestrated by the client application.

\textbf{Preparation.}
The client parses and validates each SQL recipe offline.
It verifies that every recipe is a pure \texttt{INSERT INTO \ldots\ SELECT} statement, that each one references the source table through a designated placeholder, and that no recipe contains forbidden operations such as \texttt{UPDATE}, \texttt{DELETE}, or nondeterministic expressions.
The placeholder is replaced with a filtered subquery that restricts the source to the selected \texttt{raw\_schema} scope.
Each statement is then wrapped in a PL/pgSQL \texttt{DO} block that captures the affected row count and updates a per-table counter.

\textbf{Preflight.}
The client issues a series of remote checks through SSH.
It confirms that the source and all destination tables exist, reads column metadata, loads version references from the control database, and validates that any SQL functions used in the recipes are native PostgreSQL built-ins.
Each check is a separate \texttt{psql} invocation over SSH.

\textbf{Execution.}
The client assembles all six wrapped statements into a single SQL batch, preceded by a \texttt{BEGIN ISOLATION LEVEL REPEATABLE READ} and followed by a \texttt{COMMIT}.
The batch also acquires exclusive locks on the destination tables and builds a source manifest (a hash and row count over the source scope).
A temporary timing table records \texttt{clock\_timestamp()} before and after each step, so the server-side cost of every insert is measured independently of SSH transport.
The entire batch is piped to \texttt{psql} through SSH as a single standard-input stream.

\textbf{Version registration.}
After the data commit succeeds, a second SQL batch registers a new version entry for each destination table in the control database, together with a dependency manifest that records the source scope, source versions, and the SQL recipe used.
This step runs in a separate transaction on a different database (\texttt{postgres\_data\_manager}).

\subsection{Data Model}
\label{sec:datamodel}

The source table \texttt{raw\_data} stores one row per ingested record.
Each row contains a primary key (\texttt{raw\_id}), metadata columns (\texttt{raw\_schema}, \texttt{raw\_hash}, \texttt{raw\_tab}), and a \texttt{jsonb} column \texttt{raw} whose payload holds 64 typed fields under a \texttt{values} key.

The six destination tables form a dependency graph, illustrated in Fig.~\ref{fig:dependencies}.
Two dimension tables (\texttt{table3}, \texttt{table4}) are populated first with distinct reference values extracted from the source.
A central fact table (\texttt{table1}) is then populated by joining the source against \texttt{table3}; it produces one row per source row and holds the primary foreign key back to \texttt{raw\_data}.
Three child tables follow: \texttt{table5} and \texttt{table6} each produce one row per source row by joining against \texttt{table1}, while \texttt{table6} also joins \texttt{table4}.
The final table, \texttt{table2}, unpivots up to 14 positional entries per source row through a \texttt{CROSS JOIN LATERAL}, producing a row count that can exceed the source by an order of magnitude.

All destination tables enforce referential integrity through foreign keys with \texttt{ON UPDATE CASCADE ON DELETE CASCADE}.
The six tables carry a total of eleven indexes, including primary keys, unique constraints, and partial unique indexes.
Every row inserted must satisfy these constraints and update every applicable index.

\subsection{Integrity Guarantees}
\label{sec:guarantees}

The expansion pipeline enforces several guarantees that must be preserved regardless of optimization:

\begin{itemize}
  \item \textbf{Source validation.} The source table must exist, contain the required metadata columns, and have at least one registered version for the selected \texttt{raw\_schema} scope.
  \item \textbf{Destination validation.} Each destination table must exist, and any SQL functions referenced in its recipe must be native PostgreSQL built-ins.
  \item \textbf{Relational correctness.} All foreign keys, unique constraints, and check constraints must hold after the expansion completes.
  \item \textbf{Version registration.} Each destination receives a new version entry in the control database, recording who performed the expansion, the SQL recipe used, and a dependency manifest linking the result back to the source scope and its versions.
\end{itemize}

An optimization may change \emph{how} these guarantees are enforced (for example, by validating constraints in bulk rather than per row) but may not remove them.

\section{Methodology and Results}
\label{sec:methodology}

This section presents the profiling methodology, the optimizations applied at each layer, and the measured results.

\textbf{Environment.}
The benchmark host has a 24-core AMD Ryzen Threadripper PRO 5965WX, 64\,GB DDR4, and NVMe storage.
PostgreSQL~17.2 runs inside a container with no memory limit.

\textbf{Protocol.}
The baseline uses the stock PostgreSQL configuration (128\,MB \texttt{shared\_buffers}, 4\,MB \texttt{work\_mem}).
The optimized pipeline uses a tuned configuration (2\,GB \texttt{shared\_buffers}, 256\,MB \texttt{work\_mem}, 64\,MB \texttt{wal\_buffers}, 4\,GB \texttt{max\_wal\_size}).
Before each method, the challenge database is regenerated from scratch using the deterministic generator, which guarantees that all foreign-key constraints and unique indexes are present.
The presence of all six FK constraints is verified programmatically before each baseline run.
Before each measured run, the operating system's page cache is dropped (\texttt{/proc/sys/vm/drop\_caches}) and PostgreSQL is restarted to ensure cold-cache conditions.
Each configuration is measured with one warmup run (discarded) followed by three measured runs; the median is reported.
Timing uses PostgreSQL's \texttt{clock\_timestamp()}, consistent with the application's \emph{measured processing total} metric.
The benchmark dataset contains $10^6$ source rows unless noted otherwise.

\subsection{Optimization Approach}
\label{sec:framework}

We organize the optimization space into three layers, each addressing a different level of the system.
This decomposition allows each layer's contribution to be measured independently and guides the order of implementation.

\textbf{Layer~1: Query-level} optimizations change what the SQL statements do without altering the overall execution model.
Examples include materializing extracted \texttt{jsonb} fields into a temporary table, deferring foreign-key constraints during bulk insertion, and dropping and rebuilding indexes around the insert batch.

\textbf{Layer~2: Transaction-level} optimizations change how work is batched and committed.
The expansion can be split into chunks defined by \texttt{raw\_id} ranges, each committed independently, enabling checkpoint-and-resume.

\textbf{Layer~3: Architecture-level} optimizations change the execution model itself, such as opening multiple SSH channels, replacing \texttt{INSERT \ldots\ SELECT} with \texttt{COPY}, or moving logic into a server-side PL/pgSQL procedure.

\subsection{Layer~1: Query-Level Optimizations}
\label{sec:layer1}

Based on the profiling, we applied four query-level changes and measured each in isolation before combining them.

\textbf{Foreign-key constraint removal.}
We drop all FK constraints before the insert phase and re-add them after.
The constraints are discovered dynamically by querying \texttt{pg\_constraint}, so the optimization adapts to any schema.
Re-adding the constraints validates all existing rows in bulk, which is cheaper than per-row trigger checks during insertion.
This single change yields a 2.0$\times$ speedup at $10^5$ rows.

\textbf{Index and unique-constraint removal.}
Unique indexes and constraints on destination tables are dropped before inserts and rebuilt afterwards.
Bulk \texttt{CREATE INDEX} sorts the data once~\cite{graefe2006sorting}, which is more efficient than maintaining a B-tree incrementally during insertion.
Combined with FK removal, the speedup reaches 2.4$\times$.

\textbf{Single-pass JSONB extraction with \texttt{jsonb\_to\_record}.}
Instead of letting each recipe scan the source and parse \texttt{jsonb} independently, we extract all 64 fields into a temporary table using \texttt{jsonb\_to\_record()}, which traverses each row's binary \texttt{jsonb} exactly once.
An index on \texttt{raw\_id} enables efficient range-filtered access for chunked inserts.
The extraction uses \texttt{max\_parallel\_workers\_per\_gather\,=\,4} to parallelize the scan.

\textbf{Statement rewriting with pre-cast columns.}
The recipe SQL contains patterns such as \texttt{NULLIF(BTRIM(\ldots),\,'')\allowbreak::smallint} around each field reference.
During extraction, we pre-compute these casts into typed columns and rewrite the recipe statements to reference them directly, eliminating redundant per-row text parsing during inserts.

\textbf{Position pre-computation.}
One recipe uses \texttt{CROSS JOIN LATERAL} to unpivot 14 positional entries per source row, producing 2.3$\times$ more output rows than input.
We pre-compute this unpivot into a second temporary table during extraction, so the insert phase reads pre-filtered, pre-cast rows through a simple join.

\subsection{Layer~2: Transaction-Level Optimizations}
\label{sec:layer2}

The baseline runs the entire expansion in a single transaction.
At $3 \times 10^8$ rows this transaction would run for hours, and an interruption would lose all progress.
We split the insert phase into chunks of 250K \texttt{raw\_id} rows, each committed independently.

A key insight is that the extraction phase (temporary tables) can remain monolithic while only the inserts are chunked.
This avoids re-scanning \texttt{raw\_data} per chunk.
Dimensions are populated once from the full extraction; fact and child tables are inserted per chunk from the indexed temporary table using \texttt{raw\_id BETWEEN} filters.

At 250K chunks the overhead is 13\%.
In exchange, the worst-case data loss on interruption drops from 100\% to one chunk (less than 30 seconds of work at $10^6$ rows).
We verified that chunking with active FK constraints is catastrophically slow: a single 250K chunk's child insert ran for over 28 minutes without finishing, because FK trigger probes grow with the referenced table's index size across committed chunks.
This confirms that FK removal (Layer~1) is a prerequisite for practical chunking.

We evaluated several architecture-level changes.

\textbf{PostgreSQL server tuning.}
Increasing \texttt{shared\_buffers} from 128\,MB to 2\,GB, \texttt{wal\_buffers} from 4\,MB to 64\,MB, and \texttt{max\_wal\_size} from 1\,GB to 4\,GB reduced total time by 11\% at $10^6$ rows.

We tested five additional architecture-level approaches, all of which proved slower than the single-batch temporary-table design.

The baseline scales linearly at approximately 0.166\,ms per source row.
The optimized pipeline scales sublinearly, from 0.069\,ms/row at $10^4$ to 0.033\,ms/row at $10^6$, because the fixed extraction cost is amortized over more rows and bulk index rebuilds are more efficient than incremental maintenance.
At very small scales ($< 10^4$ rows), the optimized pipeline is slower than the baseline because its fixed overhead (temporary table creation, \texttt{jsonb\_to\_record} extraction, index construction, constraint drop/rebuild) exceeds the per-row savings.

At $3 \times 10^8$ rows, the extrapolated baseline time is approximately 13.8 hours; the optimized pipeline is projected at under 3 hours.

The speedup is sensitive to the operating system's page cache state.
On hardware with large amounts of RAM (256\,GB in our HPC tests), the page cache retains the source data between runs.
In this warm-cache scenario, the baseline benefits disproportionately because its FK trigger lookups hit cached pages instead of disk, reducing the baseline to approximately 81\,s at $10^6$ rows and the speedup to $2.4\times$.
The optimized pipeline is unaffected (33\,s) because it eliminates FK triggers entirely.
The cold-cache results reported above are more representative of production deployments where the source data is not pre-cached.

\subsection{Correctness Verification}
\label{sec:verification}

We ran both the baseline and optimized pipelines on the same $10^6$-row dataset and compared the results.
Row counts match exactly across all six destination tables: 4 rows in \texttt{table3}, 27 in \texttt{table4}, $10^6$ each in \texttt{table1}, \texttt{table5}, and \texttt{table6}, and 2,321,522 in \texttt{table2} (5,321,553 total).
After the optimized pipeline rebuilds all foreign keys and unique constraints, PostgreSQL validates every row against the constraint definitions.
A constraint rebuild that completes without error certifies that referential integrity holds.
Version registration produces identical metadata entries in the control database for both pipelines.

\section{Conclusion}
\label{sec:conclusion}

We optimized the JSONB expansion pipeline of PostgreSQL Data Manager from 166\,s to 33\,s at $10^6$ source rows, a $5.0\times$ speedup measured inside PostgreSQL and excluding SSH transport.
The speedup increases with dataset size because the dominant optimizations (FK removal, bulk index rebuild, single-pass extraction) exhibit sublinear scaling.

The optimization decomposes into three independent layers.
Query-level changes (FK and index removal, \texttt{jsonb\_to\_record} extraction, statement rewriting) account for the majority of the improvement.
Transaction-level chunking adds modest overhead (13\% at 250K chunks) while enabling checkpoint-and-resume for failure recovery.
Architecture-level PostgreSQL configuration tuning provides an additional 11\%.
Five architecture-level alternatives (WAL compression, unlogged tables, PL/pgSQL procedures, \texttt{COPY} loading, and parallel SSH sessions) were tested with measurements and found slower than the single-batch approach with temporary tables, for reasons detailed in Section~\ref{sec:layer3}.

All optimizations preserve the system's integrity guarantees.
Foreign keys and unique constraints are validated in bulk after the insert phase rather than per row during it.
The relational output matches the baseline row-for-row across all six destination tables.
Source validation, version registration, and the SSH-mediated execution model remain unchanged.

\subsection*{Limitations and Future Work}

The position pre-computation currently targets the specific unpivot pattern used by the expansion recipes; a more general approach would require SQL-level pattern detection.
The application's PL/pgSQL row-count wrapper adds overhead to each insert statement, reducing the effective speedup from the theoretical maximum.

At $3 \times 10^8$ source rows, we project a baseline time of approximately 13.8 hours and an optimized time under 3 hours.
Further improvements could come from replacing the \texttt{psql} transport with a direct PostgreSQL connection through an SSH tunnel, which would eliminate process-startup overhead for each SQL batch.
